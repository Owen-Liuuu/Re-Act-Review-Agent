# D1-7 pre-registration — the one live recording of the batch route

Written before the run, so that what counts as success is fixed before anyone
sees a number. Nothing here has been executed against a model. The batch route
has never been sent to one: the repository holds two extraction recordings,
`phase6b` (14 entries) and `phase7` (23), both single-target under
`glm-4.5-flash`.

**Status: preflight PASSES against the seeded cache. Awaiting authorization.**

Every identity in this document is generated by
`eval/d1_7_preflight.py --emit-plan` into
`eval/benchmarks/melanoma_checkpoint_2017/d1_7_expected_plan.json`, which is
hash-pinned and compared by the preflight and by `tests/test_d1_7_preflight.py`.
Nothing here is typed by hand — the first draft of this document was, and every

## 1. The one harness, and the exact command

The recording runs through `eval/run_full_accuracy.py` and nothing else. It
reads the benchmark's answer key directly and never invokes `ReviewParser`, so
the parser's swallow-everything failure path (L17 in
`docs/known-limitations.md`) cannot affect this recording. That is why the eval
harness is pinned rather than `react-review run`.

```
python eval/run_full_accuracy.py \
  --config configs/config.local.yaml \
  --benchmark eval/benchmarks/melanoma_checkpoint_2017 \
  --benchmark-profile phase8_batch_v3_profile.json \
  --extraction record \
  --extraction-cache output/baselines/melanoma_checkpoint_2017/phase8_batch_extraction_cache.json \
  --semantic off \
  --out output/baselines/melanoma_checkpoint_2017/d1_7_record.json \
  --html output/baselines/melanoma_checkpoint_2017/d1_7_record.html
```

`--semantic off` is settled: the semantic cache key includes `source_value`,
`source_unit` and `source_quote` (`src/react_review/tools/compare.py:104`), and
v5 changes exactly those, so `--semantic cache-only` would miss and hard-fail.
Semantic compatibility is audited AFTER the extraction recording exists (§5).

`--out` and `--html` name paths that do not exist yet. **A path is never
reused** — overwriting the pre-fix report once already cost a `git stash` back
to recording-time code to regenerate it.

## 2. The cache the recording writes to

Not the published `phase7` cache: a recording run must not add entries to the
artifact an earlier phase is described by. The run uses a NEW file, seeded with
exactly the entries it is allowed to replay:

```
python eval/seed_extraction_cache.py \
  --from output/baselines/melanoma_checkpoint_2017/phase7_extraction_cache.json \
  --to   output/baselines/melanoma_checkpoint_2017/phase8_batch_extraction_cache.json \
  --keys-from output/d1_7_preflight.json
```

Seeded by KEY — the arm-identity lookups the preflight observed — never
wholesale. A whole-file copy would carry recordings made under other contracts
into a cache whose name says otherwise. The batch slots are deliberately left
empty; seeding one would replay an answer into a run that believes it asked for
it.

Measured on 2026-08-13: source `E0A00A5CC6F21EE3…` (23 entries) → seeded
`D3431D41EE4538CA…` (6 entries). Both hashes go in the recording manifest, so
what the run added can be told from what it started with.

## 3. What "one recording" means

One recording is ONE run of the command in §1. Pre-registered before it starts:

| | |
|---|---|
| model | `glm-4.5-flash` |
| settings | frozen in the plan as `model_settings_sha256`; `provider`, `model`, `base_url`, `temperature` (0.1), `max_tokens` (8192), `extra_body` (thinking disabled) |
| `max_attempts` | 3 — retried only for `TRANSPORT` and `NOT_JSON` |
| expected batches | **7**, §4 |
| cache before | 6 arm-identity entries; all 21 batch slots empty |

`configs/config.local.yaml` is gitignored and mutable, so pinning only the model
id would pin the smallest part of what decides the answer. The preflight reads
the non-secret settings, hashes them, and fails on drift. It never reads the
api key.

If the run does not produce a usable recording, **re-running requires a new
authorization**. "Run it again and keep the better one" is a failure this
project has already recorded once.

The cache holds **decoded JSON**, not the model's literal bytes
(`tools/extract_batch.py:262`). A `NOT_JSON` or transport failure therefore
writes **no cache entry at all** — it survives only as a classification and a
truncated detail on the batch record. Such a run is a record of a failure, and
the failed attempts are not replayable recordings. "One entry per attempt" would
be false and is not claimed.

## 5. Preflight, and the order of operations

```
python eval/d1_7_preflight.py \
  --cache output/baselines/melanoma_checkpoint_2017/phase8_batch_extraction_cache.json \
  --plan  eval/benchmarks/melanoma_checkpoint_2017/d1_7_expected_plan.json \
  --config configs/config.local.yaml
```

It must print PASS, which requires all of:

1. every `targeted_v4` lookup HIT, per claim and per attempt;
2. all 7 × 3 `targeted_v5_batch` slots empty — not only attempt 0, or a failed
   first attempt could replay a stale recording;
3. the batches identical to the plan, by claim binding and question id;
4. the model settings hash identical to the plan's.

Then, and only then:

```
extraction record, semantic OFF                  ← the only live step
→ immediately re-run with --extraction replay, assert identical
→ semantic compatibility audit: do the new source values and quotes hit the
  existing phase7 semantic cache?
     all hit  → score with --semantic cache-only
     any miss → STOP and report. A new semantic recording is a separate
                authorization; it is a second live variable.
→ grade against configs/gates/d1_batch_v1.json (§6)
→ write the recording manifest (§7) and freeze its hashes
```

## 6. What counts as passing — frozen before the result exists

`configs/gates/d1_batch_v1.json`, pinned, **provisional**. It carries the
baseline row by row, so a transition table can be computed rather than argued.

The baseline is the same benchmark under the single-target contract, replayed
offline from the phase7 recording: **66.7% (10 of 15)**, reproduced exactly and
matching the published figure. 10 rows correct, 5 refused, 0 wrong released.

**Hard conditions** — any one unmet is a FAIL, and no label accuracy offsets it:
silent releases 0; wrong-target-accepted 0; scope-wrong-released 0; batches match
the expected plan; every batched row resolves its execution id in both
directions; no forbidden transition.

**Transitions.** Allowed: `correct → correct`, `correct → refused` (a capability
loss, reported), `refused → correct`, `refused → refused`. Forbidden:
`correct → wrong_released`, `refused → wrong_released`,
`wrong_released → wrong_released`.

**Reported, never gated**: label accuracy (a system raises it by refusing less),
claims-per-batch and cost, excerpt coverage.

## 7. The recording manifest

The cache lives under `output/`, which is gitignored, so the manifest is what
enters the repository. Not a single `prompt_sha`: one batched run issues several
prompts, and one number cannot describe them.

```
model settings hash (no secrets) · provider · commit (40 chars)
run profile, benchmark profile, prompt contract, excerpt gold, expected plan,
  and gate hashes
document sha256 of every source paper
the exact command line, and the date
cache sha256 BEFORE (seeded) and AFTER, with entry counts
per prompt, sorted:  question_id · prompt_sha256 · attempt · cache_key
a set hash over that sorted list
```

## 8. What the result may and may not claim

- Report v5's measured cost. **Do not compute a speedup.** Under v5 the
  `single_extraction` bucket holds arm identities and the `batch` bucket holds

- The D6 cross-domain conclusion stays **NOT ESTIMABLE**. One study cannot move
  it, and nothing here is evidence about a third domain.
- Expect defects. Phase 7's single recording exposed a fault no test had, and
  the fix was deterministic projection over the SAME recording. Budget one such
  round before considering a re-record.

## 9. Erratum — this document was wrong twice, and the preflight was wrong twice

Recorded because both failures were the same shape, and it is the shape that
matters: **a probe not wired the way the run is wired asks a different question,
and then reports the resulting misses as evidence.**

- The first draft pinned seven `question_id`s computed while the preflight
  passed an EMPTY research context. The context reaches the prompt. They were
  fixed in the code and never regenerated in the document, so the pre-registration
  was self-invalidating on the day it was written. The plan is now a generated,
  hash-pinned file and a test compares it to the checkout.
- The preflight then reported `targeted_v4: 0/9 HIT`, and after the context fix
  `6/9`, and concluded D1-7 was BLOCKED by at least two live arm-identity calls.
  Both were artifacts: the probe built its Collector without the cohort
  registry, and the cohort display name reaches the single-target prompt. Wired
  as `eval/run_full_accuracy.py` wires it, the answer is **6/6 HIT** — the
  phase7 recording covers the arm-identity route completely, and a seeded run
  goes live for the batch route and nothing else.
- The cohort registry now has one definition, shared by the runner and the
  preflight, for the same reason the claim builder does.

The published BLOCKED conclusion, and the three-way choice that followed from
it, are withdrawn. There is no need for two authorizations: §2 seeding plus §5
preflight gives a single-variable recording in one run.
